# Research and Select Resources for a Specific Purpose

Help the user make a choice and understand how to start. Base selection on intended use, existing resources, and operating experience. Popularity, feature count, and the number of results do not establish suitability. The user is the person requesting the task; if someone else will use the resource, account for that person's requirements too.

## Establish the task

Extract from the request and available context:

| Area | What to establish |
|---|---|
| Purpose | What the user wants to accomplish and the required deliverable or file format |
| Actual users | Who will use the resource and their existing knowledge and operating experience |
| Conditions | Device, language, budget, time, data handling, and other feasibility constraints |
| Selection criteria | Mandatory conditions versus preferences |

Ask only for missing information that would change the selection. State adjustable assumptions for less consequential gaps. Do not ask for information already provided or carry constraints such as “free” or “local processing only” from a past task into a new one. A project the user currently works on does not establish a personal interest or lasting preference.

For example, when selecting a subtitle tool for offline video processing on a Mac, check operating-system support, whether video uploads are required, and export options. A “free subtitle tool” label is not sufficient.

## Gather and verify the actual content

Use available search, page-reading, platform connectors, or local-file tools without requiring a particular plugin. Compare supplied material directly when it is sufficient. Do not browse if the user requests offline work or restricts the task to supplied sources.

Prefer project websites, repositories, actual documentation, download pages, and demos. Discussions and reposts can reveal leads, but verify decision-critical capabilities and limitations against original sources. When a decision requires current pricing, platform support, licensing, or access terms, check current sources within the user's permitted scope. Mark unverifiable claims as unknown; do not present old information as current fact.

For candidates that could affect the choice, establish:

| Check | What to inspect | Avoid this mistake |
|---|---|---|
| Resource type | Finished product, source-code project, document, asset, library, or concept demonstration | Presenting a low-level tool as a ready-to-use product |
| Available content | Full content, source code, models, a demo, exported files, or only a landing page | Conflating a product idea, a demonstration prototype, and a usable product |
| Conditions of use | Free-tier coverage and requirements for paid APIs, accounts, hardware, or additional tools | Treating free registration as free task completion, or visible source code as a verified license |
| Evidence of fit | Evidence of suitability, remaining gaps, and necessary adaptations | Inferring suitability from a name, popularity, or marketing claim |

Record sources and the date of review. Distinguish a source's claim, inspected content or code, an opened demo, and an actual execution test. Do not substitute one evidence level for another. If a tool fails, access is denied, or content is empty, retain the gap and use another available source or stop checking that item; do not retry indefinitely.

Assess evidence level separately from suitability. When documentation supports all mandatory conditions, a recommendation may be labeled “supported by documentation, not runtime-tested.” Require runtime testing for inclusion only when the user requests it or a critical condition cannot otherwise be established. Do not treat unknown critical costs or compatibility as satisfied.

## Compare and select

- Apply mandatory conditions before preferences. Do not recommend a resource as qualified if it fails a mandatory condition. Keep candidates with unknown critical conditions pending verification.
- Explain specific reasons for inclusion or exclusion. There is no need to deliver every link found.
- Consolidate different entry points for the same project while retaining their purposes. Do not count a homepage, documentation site, and repository as three independent resources.
- Separate facts, suitability judgments based on those facts, and adaptation proposals. If nothing fits, state the gap instead of filling a quota or silently relaxing constraints.
- Scale research depth to the task. Stop when the evidence supports a choice and explains the important gaps. A research-only request does not authorize installation, purchase, registration, deployment, or modification. Carry out explicitly requested follow-up work within its authorized scope.

## Deliver and check

Lead with the selection and its rationale, then provide the comparisons needed to assess it. Choose table columns for the task; useful fields include the resource and source, available content, conditions of use, reasons it fits, limitations, and verification level. Add an entry point or a minimal trial procedure when helpful.

Keep implementation detail subordinate to the decision. When options have different strengths, explain which situation each suits instead of inventing precise scores or a single definitive ranking.

Before delivery, check:

| Check | Passing criterion |
|---|---|
| Requirements | Recommendations meet mandatory conditions; unknowns are clear |
| Accuracy | Free-tier coverage, resource type, and verification level are not overstated |
| Traceability | Decision-critical conclusions link back to specific sources |
| Decision usefulness | The user knows why to choose an option, when not to choose it, and what to do next |

## Example requests

“Use purpose-led-resource-research to find open-source screen recorders for product demos. They must support Mac, system audio, and watermark-free video export. Explain costs and licensing conditions.”

“Using only the material I provide, compare subtitle tools for Mac support, local processing, and SRT export. Mark unsupported capabilities as pending verification.”
