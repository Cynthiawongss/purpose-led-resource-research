# 按实际用途搜集和筛选资源

让用户能根据结果作出选择，并知道下一步怎样开始。以使用目的、现有条件和操作经验为筛选依据；资源数量、知名度和功能数量不能代替适用性判断。用户指提出任务的人；如果资源交给其他人使用，还需考虑实际使用者的条件。

## 确定这次要解决的事

从当前请求和已有上下文提取：

| 要确认的内容 | 需要明确什么 |
|---|---|
| 使用目标 | 要完成什么，最终需要什么成果或文件 |
| 实际使用者 | 谁来使用，已有的知识和操作能力 |
| 使用条件 | 设备、语言、预算、时间、数据处理方式等 |
| 取舍标准 | 哪些必须满足，哪些只是偏好 |

只追问会改变筛选结果的缺失信息。其余使用可调整的假设，明确说明。不要让用户重复提供已有信息，也不要把过去某次任务的“免费”“仅限本地运行”等条件自动带入新任务。用户当前负责的项目不等于其个人兴趣或长期偏好。

例如：为需要在 Mac 上离线处理视频的用户选择字幕工具，先检查系统支持、视频是否必须上传和字幕导出方式，不能因为标注“免费字幕工具”就认定适合。

## 搜集并核实实际内容

按当前可用能力选择搜索、网页读取、平台连接器或本地文件工具，不依赖特定插件。已提供足够材料时，可以直接基于材料比较；用户要求离线或只用给定资料时，不联网。

优先核对项目官网、仓库、实际文档正文、下载页或演示；讨论和转载可帮助发现线索，但涉及关键能力和限制时回到原始来源。需要判断当前费用、支持平台、许可证和访问条件时，在用户允许的范围内核对最新来源；无法核对就标明未知，不把旧资料当成当前事实。

对影响选择的候选项，查清：

| 核实项 | 查什么 | 避免误判 |
|---|---|---|
| 资源类型 | 成品、源码项目、文档、素材、技术库或概念展示 | 不把底层工具当成可直接使用的成品 |
| 实际可得内容 | 正文、源码、模型、演示、导出文件，还是只有介绍页 | 分清产品设想、演示原型和实际可用的产品 |
| 使用条件 | 免费范围，付费接口、账号、设备及额外工具要求 | 免费注册不等于免费完成目标；源码公开不等于许可已确认 |
| 适用依据 | 符合用户目标的证据、差距和必要改造 | 不凭名称、热度或宣传语判断适合 |

记录来源及本次核查时间。区分“来源声称”“已读取正文或源码”“打开过演示”“实际运行验证”；不能把其中一种写成另一种。工具返回失败、无权限或空内容时，保留缺口，改用可用来源或结束该项核查，不无限重试。

证据等级与适用性分别判断：文档支持全部必须条件时，可以给出“基于文档的推荐，尚未实测”；只有用户明确要求实测或关键条件必须运行才能确认时，才把实测作为入选门槛。费用、兼容性等关键条件仍未知时，不按符合条件推荐。

## 比较与取舍

- 先按必须条件筛选，再比较偏好。必须条件不满足的资源不能排为合格推荐；关键条件未知的资源列为待核实候选。
- 说明入选或排除的具体理由；不需要把搜到的所有链接都交付。
- 合并同一项目的不同入口，同时保留各入口用途。不要把产品首页、使用文档和仓库重复计为三项独立资源。
- 将事实、基于事实的适用性判断和改造建议分开。没找到合适资源时如实说明缺口，不凑满数量或暗中放宽条件。
- 按需求规模控制调研深度。有足够证据支持选择、说明关键差距后即可收束。仅收到调研请求时，不自动安装、购买、注册、部署或改造候选项目；用户已明确要求的后续工作按授权范围执行。

## 交付

先给选择建议及其依据，再提供必要的对照信息。表格列按任务选用，通常包含：资源及来源、实际可得内容、使用条件、适用理由、限制、核实程度。需要时附下一步入口或最小体验步骤。

避免用大量技术细节淹没决策信息。若多个候选各有优势，按适用情境给出选择，不编造精确评分或唯一排名。

交付前检查：

| 检查项 | 通过标准 |
|---|---|
| 条件符合 | 推荐满足必须条件，未知项明确 |
| 表述准确 | 免费范围、资源类型和核实程度没有夸大 |
| 来源可查 | 关键结论能追溯到具体来源 |
| 能作选择 | 用户知道为什么选、什么时候不选，以及下一步做什么 |

## 使用示例

“使用 purpose-led-resource-research，找可用于产品演示的开源录屏工具，支持 Mac、录制系统声音和导出无水印视频，说明费用与许可条件。”

“只根据我提供的材料，比较几个字幕工具是否适合 Mac、本地处理和导出 SRT；没有证据的能力标为待核实。”
